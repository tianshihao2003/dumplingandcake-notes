## 第 1 版图（PPT 第 2 页）：骨架只有四个方框

第 1 页是封面（「Web 后端开发 / 总结」），第 2 页就是这张图的**起点**——整张图只有四个方框，最左边是一个浏览器图标（代表"发起请求的一方"），右边四个方框从左到右排成一条线：

```text
浏览器
  │ 请求
  ▼
Controller ──▶ Service ──▶ Dao ──▶ MySQL
  ◀──────────── 响应 ─────────────┘
```

这四个方框就是[三层架构](/posts/编程学习/javaweb学习笔记/37-三层架构/)加上数据库，各层职责是第 4 章定的：

| 方框 | 全称 | 职责 | 这一层后来用什么技术实现 |
| --- | --- | --- | --- |
| **Controller** | 控制层 | 接收前端发送的请求，对请求进行处理，并响应数据 | SpringMVC（第 [33](/posts/编程学习/javaweb学习笔记/33-springboot获取请求数据/)、[35](/posts/编程学习/javaweb学习笔记/35-springboot设置响应数据/) 篇） |
| **Service** | 业务逻辑层 | 处理具体的业务逻辑 | Spring 容器里的 bean + IOC/DI（[38](/posts/编程学习/javaweb学习笔记/38-分层解耦与ioc-di入门/)、[39](/posts/编程学习/javaweb学习笔记/39-ioc与di详解/) 篇） |
| **Dao** | 数据访问层，也叫持久层 | 负责数据访问操作，包括数据的增、删、改、查 | MyBatis（[51](/posts/编程学习/javaweb学习笔记/51-mybatis入门与辅助配置/)～[55](/posts/编程学习/javaweb学习笔记/55-mybatis-xml映射配置/) 篇） |
| **MySQL** | 数据库 | 数据存储和管理 | MySQL + SQL（[40](/posts/编程学习/javaweb学习笔记/40-数据库概述与mysql入门/)～[48](/posts/编程学习/javaweb学习笔记/48-dql排序与分页查询/) 篇） |

> [!IMPORTANT]
> 记住这张**骨架**比记住任何一个技术都重要：后面点亮的 11 个技术，全都是挂在四个方框上下的"配件"。Tlias 工程的包结构（`controller` / `service` / `mapper` / `pojo`）就是这张图的落地写法（[57 篇](/posts/编程学习/javaweb学习笔记/57-tlias项目准备与开发规范/)）。

### 上方那一排：都是"横切"进业务里的能力

IOC、DI、AOP、事务管理、全局异常处理排在三层**上方**，这个位置很有意思——它们不属于某一层，而是**横切**在层与层之间：Controller 里要能拿到 Service 对象（DI 注入），Service 的方法上要能开启事务（事务管理），所有方法外要能包一层公共逻辑（AOP），所有异常要能在最外层被接住（全局异常处理）。它们都由 Spring 框架提供，所以第 4 页会把它们圈进同一个框里。

### 下方那一排：进出的"标记"与"外围资源"

会话、令牌、云存储、持久层框架排在三层**下方**，它们都和"数据怎么流转"有关：

- **Cookie/Session 与 JWT** 管的是"**这个人是谁**"——先有标记，才谈得上拦（[82 篇](/posts/编程学习/javaweb学习笔记/82-会话技术与jwt令牌/)把这条依赖讲得很清楚）；
- **阿里云 OSS** 管的是"**文件存哪**"——业务数据进 MySQL，文件类数据进 OSS；
- **MyBatis** 管的是"**数据怎么进 MySQL**"——它紧挨着 Dao 和 MySQL 之间。

### 左边那两道门：先拦请求，再进业务

**过滤器 → 拦截器 → Controller** 这个先后顺序不是随便排的：Filter 是 Servlet 规范里的组件，请求**还没进 SpringMVC** 就被它经手；Interceptor 是 SpringMVC 内部的机制，请求**已经到了 SpringMVC、正要调用 Controller 方法**时才轮到它（[84 篇](/posts/编程学习/javaweb学习笔记/84-拦截器interceptor/)有一节专门把两者摆在一起对比）。所以登录校验的两套方案写的是同一段逻辑，位置却不一样。

## 第 3 版图（PPT 第 4 页）：按三条线归类，下面垫上 SpringBoot

第 4 页把散落的词**收进框里**，图上出现四个区域名：

- **JavaWeb 解决方案**（左边一列，两格）：过滤器 ／ Cookie、Session ／ JWT ／ 阿里云 OSS
- **Spring framework**（中间一大格）：IOC、DI、AOP、事务管理，下面还留着一个写着 **web** 的小格（里面是拦截器、全局异常处理）
- **Mybatis**（右边一列）：Mybatis
- **SpringBoot**（最下面一条横贯中间与右边）：SpringBoot

| 区域 | 里面装着什么 | 为什么归在一起 |
| --- | --- | --- |
| **JavaWeb 解决方案** | 过滤器、Cookie、Session、JWT、阿里云 OSS | 共同点是"**通用方案，不靠 Spring**"——过滤器来自 Servlet 规范（JavaWeb 三大组件之一），Cookie/Session 来自 HTTP 的会话技术，JWT 是令牌标准，OSS 是第三方云服务 |
| **Spring framework** | IOC、DI、AOP、事务管理 + 下面的 web 格（拦截器、全局异常处理） | 这是 Spring 框架自己的核心能力：管对象（IOC/DI）、管切面（AOP）、管事务（事务管理），以及 web 支持 |
| **Mybatis** | Mybatis | 持久层框架单独占一列——它不归 Spring 管，SpringBoot 只是帮它做好自动配置 |
| **SpringBoot** | SpringBoot | 底座：它不写业务，靠**起步依赖 + 自动配置**把上面这些技术组装好、把应用拉起来（[89 篇](/posts/编程学习/javaweb学习笔记/89-springboot自动配置原理/)） |

这一页最值得记住的是**"web"那一小格**：拦截器和全局异常处理被从上面一排挪进了 Spring framework 的 web 位置——它们不是泛泛的 Spring 能力，而是 **web 层**的东西。第 5 页这个判断被坐实了。

## 第 4 版图（PPT 第 5 页）：SpringMVC 补上最后一块，图完整了

第 5 页把上一步那个 **web** 小格写成了正式的名字——**SpringMVC**，并往里补了两个词：**接收请求**、**响应数据**。于是最终版的长这样：

```text
JavaWeb 解决方案            Spring framework                     Mybatis
  过滤器                    SpringMVC ← 接收请求、响应数据          Mybatis
  Cookie、Session                    拦截器、全局异常处理
  JWT                       IOC、DI、AOP、事务管理
  阿里云 OSS
───────────────────────────────────────────────────────────────────────
                       SpringBoot（起步依赖 + 自动配置）
```

SpringMVC 这一格里的四个词，正好对应后端基础里讲"收请求、发响应"的那几篇：

| 图上的词 | 它是什么 | 笔记 |
| --- | --- | --- |
| **接收请求** | 服务器收到 HTTP 请求（请求行、请求头、请求体），SpringMVC 解析后交给对应的 Controller 方法，参数自动绑定 | [32](/posts/编程学习/javaweb学习笔记/32-http协议与请求数据格式/)、[33 篇](/posts/编程学习/javaweb学习笔记/33-springboot获取请求数据/) |
| **响应数据** | Controller 返回的对象被转成 JSON 写回浏览器（项目里统一包成 `Result`） | [34](/posts/编程学习/javaweb学习笔记/34-http响应数据格式与状态码/)、[35 篇](/posts/编程学习/javaweb学习笔记/35-springboot设置响应数据/) |
| **拦截器** | 拦截控制器方法的执行（登录校验的第二套方案） | [84 篇](/posts/编程学习/javaweb学习笔记/84-拦截器interceptor/) |
| **全局异常处理** | 把所有异常统一处理成 `Result` 格式 | [76 篇](/posts/编程学习/javaweb学习笔记/76-全局异常处理/) |

> [!IMPORTANT]
> 这一格解开了一个常见困惑：**Controller 层的"接收请求、响应数据"这活，实际是 SpringMVC 在干**。`@RestController`、`@RequestMapping`、`@RequestBody`、`@RequestParam` 这些注解都是 SpringMVC 的；[39 篇](/posts/编程学习/javaweb学习笔记/39-ioc与di详解/)里那句"声明控制器 bean 只能用 `@Controller`（或 `@RestController`），因为 SpringMVC 要认出哪些类是请求处理类"，说的就是这层关系。

### 把图读成一条链路

把四版图叠起来，一条请求的走向就是**从左边进入、穿过三层、到右边的数据库、再原路返回**：

```text
浏览器
  │  ① 请求（请求头里带着 JWT 令牌）
  ▼
过滤器 Filter                                        ← 第一道门（JavaWeb 解决方案那一列）
  │
  ▼
拦截器 Interceptor ──▶ Controller                     ← 第二道门 + 控制层（都在 SpringMVC 这一格里）
  │                        ▲
  │                        │  接收请求 / 响应数据由 SpringMVC 负责
  ▼                        │
Service ──▶ AOP 代理（事务管理 / 记录操作日志）          ← 业务逻辑层
  │
  ▼
Mapper（MyBatis）──▶ MySQL                            ← 数据访问层 + 数据库
  │
  └── ② 响应：Result 由 SpringMVC 转成 JSON 原路返回浏览器
      ③ 中途任何异常 ──▶ 全局异常处理 ──▶ Result
      ④ 文件类数据 ──▶ 阿里云 OSS（不进 MySQL）
      ⑤ 上面这一切能跑起来 ──▶ SpringBoot（起步依赖 + 自动配置 + 内嵌 Tomcat）
```

## 小结

| 问题 | 答案 |
| --- | --- |
| 这张图的骨架是什么？ | 三层架构 + 数据库：Controller（接收请求、处理请求、响应数据）→ Service（业务逻辑处理）→ Dao（数据访问）→ MySQL（数据存储） |
| 图上第一道门、第二道门分别是谁？ | 过滤器 Filter（Servlet 规范，请求还没进 SpringMVC）→ 拦截器 Interceptor（SpringMVC 内部，拦控制器方法） |

## 练习题

### 一、知识回顾（读完直接做下面的实践题）

下面 12 条就是整张地图的"关键点清单"，每条都给出"这个技术解决什么问题、在哪一层"。合上笔记，逐条问自己能不能说出来；说不出来的，点回对应笔记再看一眼。

1. **三层架构 + 数据库（图的骨架）**：Controller（控制层）**接收前端发送的请求，对请求进行处理，并响应数据**；Service（业务逻辑层）**处理具体的业务逻辑**；Dao（数据访问层/持久层）**负责数据的增、删、改、查**；MySQL 负责**数据存储和管理**。调用方向是单向的 Controller → Service → Dao → MySQL（37 篇）。
2. **IOC / DI（横在三层上方）**：解决"层与层之间焊死"的耦合问题——**IOC（控制反转）**把对象的创建控制权由程序转移到 Spring 容器，**DI（依赖注入）**让容器把运行所需的资源（对象）注入进来；目标是**高内聚低耦合**（38、39 篇）。
3. **AOP（横在三层上方）**：**面向特定方法编程**——把"统计方法耗时""记录操作日志"这类公共逻辑从业务方法里抽走，由代理对象在**指定方法执行前后自动运行**，业务方法一行都不改（85-87 篇）。
4. **事务管理（横在三层上方）**：**一组操作的集合，一个不可分割的工作单位，要么同时成功、要么同时失败**；用在 Service 的多表操作上做兜底（新增员工要同时写 `emp` 和 `emp_expr`），Spring 用 `@Transactional` 管（70、71 篇）。
5. **全局异常处理（横在三层上方）**：异常不可避免，而默认返回的 `{"timestamp","status","error","path"}` **不符合项目规范**；用一个全局异常处理器把异常统一转成 `Result`，前端永远只处理一种响应形状（76 篇）。
6. **过滤器 Filter（Controller 左边的第一格）**：**JavaWeb 三大组件（Servlet、Filter、Listener）之一**，把对资源的请求**拦截**下来做通用操作——**登录校验、统一编码处理、敏感字符处理**；它在 Servlet 层干活，请求还没进 SpringMVC（83 篇）。
7. **拦截器 Interceptor（过滤器右边、Controller 之前）**：**Spring 框架提供的、动态拦截控制器方法执行**的机制，在指定方法调用前后执行预设代码；**接口规范不同**（实现 `HandlerInterceptor`，而过滤器实现 `Filter`）、**拦截范围不同**（过滤器拦所有资源，拦截器只拦 Spring 环境中的资源）是它与 Filter 的两点区别；靠配置类的 `addPathPatterns` / `excludePathPatterns` 决定拦哪些、放哪些，粒度更细（84 篇）。
8. **MyBatis（贴着 Dao 与 MySQL）**：持久层框架——Dao 里只写**接口 + 注解/XML 映射**，参数封装、结果映射、连接池都替我们做了，不再手写 JDBC 那套样板代码（51-55 篇）。
9. **SpringMVC（Spring framework 的 web 格）**：Spring 框架里的 **web 层**，负责**接收请求**（把 HTTP 请求参数绑定到方法参数）与**响应数据**（把返回对象转成 JSON）；**拦截器、全局异常处理也归它这一格**（32-35、76、84 篇）。
10. **Cookie/Session 与 JWT（三层下方）**：登录校验的第一件事——**登录标记**。Cookie 存在客户端、Session 存在服务端，两者都受"服务端会话"的限制；课程最终选**令牌（JWT）**——登录成功后生成令牌返回前端，之后每次请求在请求头里带上，配合统一拦截校验（81、82 篇）。
11. **阿里云 OSS（三层下方）**：**第三方云存储服务**，业务数据进 MySQL，文件类数据进 OSS；引出的"参数配置化"还顺手解决了密钥写死在代码里的问题（72、73 篇）。
12. **SpringBoot（最下面的底座）**：两大能力是**起步依赖**与**自动配置**，加上**内嵌 Tomcat**，一个 `main` 方法就能把 Web 应用跑起来；正因为它是底座，才托得住 Spring framework 与 MyBatis 这两列（31、88-90 篇）。

  > **1. 进门**：请求在**请求头**里带着登录成功时拿到的 **JWT 令牌**。先过**过滤器 Filter**（Servlet 规范，JavaWeb 解决方案那一列），再过**拦截器 Interceptor**（SpringMVC 那一格）。令牌不合法的话，在**过滤器（或拦截器）这一步**就被挡住、直接返回 401，**根本进不到 Controller**——这正是"统一拦截"的意义：几十个接口不用各写一遍校验（83、84 篇）。
  > **2. 收参**：这一步是 **SpringMVC** 干的（图上"接收请求"）。普通表单字段靠 `@RequestParam` 一类的方式绑定到方法参数；**头像文件**用 `MultipartFile` 接收，按 72/73 篇的流程先上传到**阿里云 OSS**，拿回一个可访问的 URL；工作经历是多行数据，用对象/集合接收。
  > **3. 调业务**：Controller **不自己 `new`**，而是用**依赖注入**拿容器创建好的 Service 对象；Service 里同样注入 Mapper。负责这两个词的是 **IOC（创建权交给容器）** 和 **DI（容器把依赖注入进来）**，对应图上横在三层上方的前两格（38、39 篇）。
  > **4. 业务里挂着的两件事**：① **事务管理**——`emp` 和 `emp_expr` 两张表要么一起成功、要么一起失败，方法上加 `@Transactional`，避免出现"基本信息存了、工作经历没存"的残缺数据（70、71 篇）；② **AOP**——在方法前后自动织入公共逻辑，这里用来**记录操作日志**（谁、什么时候、做了什么），业务代码一行都不改（87 篇）。顺带 `@Transactional` 本身也是靠 AOP 代理实现的。
  > **5. 落库**：Service 往下调 **Mapper**（持久层/数据访问层），它是 **MyBatis** 的接口——只写接口方法 + 注解或 XML 映射，SQL 里的 `#{}` 负责参数封装、结果自动映射成对象、连接交给**数据库连接池**，不用手写 JDBC 的注册驱动/获取连接/释放资源那一套（51-55 篇）。SQL 最终发到 **MySQL**，数据落在 `emp`、`emp_expr` 两张表里。
  > **6. 出错**：唯一约束冲突的异常由 **Dao/Service 这一层抛出**，一路往上到 Controller；**全局异常处理器**（SpringMVC 那一格）把它接住，转成统一响应，前端收到的是
  >    ```json
  >    {"code":0,"msg":"...","data":null}
  >    ```
  >    而不是 SpringBoot 默认的 `{"timestamp","status","error","path"}`（76 篇实测过默认结构）。
  > **7. 回程**：Controller 返回的 `Result` 对象由 **SpringMVC（响应数据）** 转成 JSON 写回浏览器——这一步和第 2 步是同一格的两个方向（34、35 篇）。
  > **8. 归类**：
  > - **JavaWeb 解决方案**：过滤器（拦请求、校验令牌）；
  > - **Spring framework**：IOC/DI（造对象、注入依赖）、AOP（记日志）、事务管理（两表一致），以及 **SpringMVC** 那一格（接收请求、响应数据、拦截器、全局异常处理）；
  > - **Mybatis**：数据访问，SQL 与结果映射；
  > - **SpringBoot**：把这些技术**组装起来并跑起来**——一行起步依赖把 web 相关的一整套 jar（含内嵌 Tomcat）带进来，自动配置把 MyBatis、SpringMVC 这些配好，所以它是**底座**；`application.yml` 里的数据源参数、Bean 的创建与作用域，都归它管（31、56、88-90 篇）。
  >
  > 一句话收尾：**这条链路就是整张图在动**——浏览器从左下角进，穿过两道门（Filter、Interceptor）进入 SpringMVC，沿着三层架构往下走到 MySQL，再原路带着 `Result` 回到浏览器；图上的每一个技术都对应链路上的一个环节，没有一个词是白画的。
